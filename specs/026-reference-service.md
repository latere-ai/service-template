# Reference service

## Problem

A template is verified by the promises it makes, and promises are checked one
spec at a time. Nothing in the deck so far proves the parts compose. Integration
defects between them, a lint rule that fires on the generated skeleton, a
prerender step that breaks the embedded serving path, a coverage gate the
scaffold cannot pass, appear only when a real service is built from the whole
thing.

A template with no working example also gives an evaluator nothing to read.

## Scope

A complete, small service generated from the template and kept working in CI.

## Design

### What it is

A minimal service that exercises every feature flag: an authenticated interface
over a persisted resource, a public prerendered marketing route, an
authenticated application route, two locales, and a full delivery pipeline to a
pre-production target.

It stays small on purpose. A large example becomes a product with its own
backlog and stops tracking the template.

### How it is built

The example is generated by `template init`, not written by hand. A test
regenerates it and compares against the committed tree, so the example cannot
drift from the generator, and a change to the skeleton that breaks generation
fails immediately.

### What it proves

| Property | Proof |
| --- | --- |
| The scaffold passes its own gates | The example runs the full verify pipeline |
| The gates are real | Mutation fixtures each break exactly one gate |
| Delivery works end to end | A tagged pre-release deploys and smokes on a schedule |
| Documentation is accurate | The documented quick start runs in a test |
| Upgrade works | The example is upgraded across template versions in CI |

The mutation fixtures matter most. For each gate, a branch introduces the defect
the gate exists to catch, and a test asserts that gate and only that gate fails.
This is how the deck avoids gates that pass everything.

### Upgrade rehearsal

Every template release runs `template upgrade` on the example from the previous
release and requires the result to pass. The upgrade path is therefore tested on
every release rather than discovered by the first consumer who tries it.

## Acceptance criteria

1. The example is byte-identical to a fresh `template init` with its
   configuration.
2. It passes the full verify pipeline, including the coverage gate.
3. One mutation fixture exists per gate, and each fails that gate alone.
4. A scheduled release deploys it to pre-production and produces a complete
   evidence block.
5. `template upgrade` from the previous release passes on every release.
6. The documented quick start runs unmodified in a test.
